Overview

I redesigned and rebuilt the Create and Edit User pages that enterprise banks use to manage their users’ full profiles, from the first requirements through to the API. A project that pulled in all three layers: design, front end and back end.

  • Role: UX, front end and back end
  • Stack: Angular, TypeScript, RxJS, C# .NET
  • Timeline: 2026 (in UAT)

User management is where bank admins create and edit the people who use the platform: their details, the parts of the bank they work in, the centres they can access, and what they’re allowed to do.

The old page was one long form that grew every time the platform added a new product offering. Then a new client came on board at a far larger scale than anything before, with some users needing access to 1,000+ centres. The old page couldn’t cope, in speed or in usability.

The challenge

For a user with 1,000+ centres, the page took around 60 seconds to load. Three things made it slow and hard to use:

  • One long form: every setting lived on a single page, and it kept growing as new product offerings were added.
  • One heavy endpoint: the page fetched everything about a user in a single call, whether the admin needed it or not.
  • Separate dropdowns: centres and subcentres were picked from two separate dropdowns. With thousands of options they were hard to search, and it was almost impossible to see which subcentre belonged to which centre.

Underneath it all were the data relationships between centres, subcentres and users, which the API and the UI both had to handle cleanly.

My role

I owned it end to end, across all three layers. I worked in a small pod with a principal engineer, a full-stack engineer and a senior QA analyst, plus a product owner who looks after several pods.

  • Planning: requirements analysis, story writing and estimates, working out what admins actually needed before designing anything.
  • Design: prototyping and UX, using AI-assisted design to explore options quickly.
  • Front end: the Angular rebuild, including the centre hierarchy, bulk selection, and the line between local and saved state.
  • Back end: API changes in the Profiles service.

Design

From one long form to four focused tabs

I split the long form into four focused tabs in a side nav. The user’s name and account status sit at the top of it, and managers can activate or deactivate the account from there.

  1. User details: name, email and user level.
  2. Business units: users often belong to several, so they’re added with a typeahead and listed below it.
  3. Access centres: the heaviest tab: a home centre plus any extra access, with bulk select and deselect. The search here gets its own section below.
  4. Groups & roles: what a user can do, including roles inherited from any groups they belong to.

Each tab is self-contained and has its own Save button, so a new client-specific feature can become a tab instead of making the form longer again.

One search for centres and subcentres

The design work I’m proudest of is the centre search. Merging two dropdowns into one search meant supporting two different ways of looking:

  1. I know the subcentre: search for it by name and add it to the user.
  2. I only know the parent centre: search for the centre, then browse its subcentres and pick one or many.

I explored it in Claude Design, starting broad. Early prototypes like these put very different layouts side by side, and because they were live, I could type into each one and feel the trade-offs. From there I honed in on the strongest direction and refined it over many more rounds of mockups until it felt right.

Results show as a nested list, with subcentres grouped under their parent. A search term often matches a subcentre but not its parent, so the API adds the parent centre into the results whenever one of its subcentres matches. That keeps every result in context.

Each parent centre in the results also has a button that opens all of its subcentres in a popup, and so does the Manage subcentres link on each centre the user already has. From there, admins can search within that centre, select all of its subcentres at once, or make individual tweaks. Results load as you type, and more load in automatically as you scroll.

The speed-up came from the back end as much as the front end.

  • Split the endpoint: I broke the single heavy endpoint into focused APIs, one per tab. Each tab loads its own data separately, so the first load only fetches what’s on screen. The biggest gain was on the Access centres tab.
  • Search that keeps context: the centre search API returns matching subcentres together with their parent centre, even when the parent itself doesn’t match.
  • Optimised queries behind those APIs, so each call returns just what the screen needs.
  • Caching where it helps, so switching back to a tab you’ve already opened is faster.
  • A lean front end: the Angular side requests data as the admin types and scrolls, and keeps unsaved selections in local state until the admin saves.

Impact

For a user with 1,000+ centres, the page now loads in under 3 seconds instead of around 60, roughly 95% faster.

  • Admins work through one focused tab at a time instead of one long form, and find centres by searching instead of scrolling.
  • The tab structure leaves room for client-specific features later.
